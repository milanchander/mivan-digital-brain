# Extraction Summary — MEDIRTR0

MEDIRTR0 is a **batch** COBOL driver named "MiEDI LOB Claim Router." OBSERVABLE:
it reads a sequential file of edited claims, determines a line-of-business (LOB)
code for each, writes the claim to one of three sequential output files
(Commercial → MiCPS, MA → MiFCT, Medicaid → MiFCT), and inserts a routing-audit
row into DB2 `ROUTING_AUDIT`. It is the concrete implementation behind the L3
ghost node **FACETS-LOB-ROUTING-TABLE**.

Headline of the risk assessment: **HIGH risk / migration BLOCKED.** Two things
drive this. (1) The source contradicts the current L3 documentation in ways that
matter — the L3 "LOB Routing Architecture" says routing is by member-ID lookup
with **effective-date logic for mid-year LOB changes**, but the source routes on
**CMS-contract-ID prefix + payer-contract lookup with NO effective/term-date
check at all** (OBSERVABLE, `3200-CHECK-PAYER-CONTRACT`). (2) All three COPYBOOKs
and two threshold literals are absent from the material provided, so record
layouts and limit values **cannot be determined from source**.

## Business Logic

`0000-MAIN` (OBSERVABLE): `PERFORM 1000-INIT`, then `2000-PROCESS UNTIL
END-OF-FILE`, then `9000-FINALIZE`, `STOP RUN`.

`1000-INIT` (OBSERVABLE): opens all five files, checks each FILE STATUS, ABENDs on
any non-zero, initializes counters, reads first record.

`2000-PROCESS` (OBSERVABLE): per record — increment claims-read, then
`3000-DETERMINE-LOB` → `3500-CHECK-CLAIM-AGE` → `4000-ROUTE-CLAIM` →
`5000-WRITE-AUDIT`, then read next.

`3000-DETERMINE-LOB` (OBSERVABLE): three-tier cascade — clear `WS-LOB-CODE`, try
`3100` (CMS contract), then `3200` (payer contract) only if undetermined, then
`3300` (default) only if still undetermined.

`3100-CHECK-CMS-CONTRACT` (OBSERVABLE structure; mapping rationale INFERRED):
if `ECL-CMS-CONTRACT-ID` not spaces, `EVALUATE` its first character:
- `H`, `R`, `S`, `E` → `MA`  |  `N` → `MC`  |  OTHER → CONTINUE (undetermined)
- sets `WS-ROUTE-METHOD = 'CMS-ID'` when determined
- Source comment: *"CMS contract ID prefix identifies Medicare Advantage plan
  type."* **INFERRED (LIKELY)** that H/R/S/E denote MA plan types and N denotes
  Medicaid per CMS contract-ID conventions — *evidence to confirm:* the CMS
  contract-ID numbering scheme and Mivan's actual plan inventory. Do not treat
  the specific prefix→LOB mapping as verified without SME sign-off.

`3200-CHECK-PAYER-CONTRACT` (OBSERVABLE): moves `ECL-PAYER-CONTRACT-ID` to
`PCT-CONTRACT-ID`, reads `PAYER-CONTRACT`; on INVALID KEY → CONTINUE (undetermined);
on NOT INVALID KEY, if `PCT-STATUS-CD = 'AC'` → `WS-LOB-CODE = PCT-LOB-CODE`,
`WS-ROUTE-METHOD = 'CONTRACT'`.
- **OBSERVABLE GAP:** there is **no check that `ECL-DOS-FROM` falls within
  `PCT-EFFECTIVE-DT`…`PCT-TERM-DT`.** The contract's LOB is applied regardless of
  service date. *Impact (INFERRED, PLAUSIBLE):* mid-year LOB changes route on the
  contract's current LOB, not the LOB in effect on the date of service — a
  mis-routing risk. **This directly contradicts the L3 doc** ("mid-year LOB
  changes are handled by effective date logic"). *Evidence to resolve:* SME
  confirmation of whether the effective-date check lives upstream, elsewhere, or
  is a genuine defect.

`3300-APPLY-DEFAULT` (OBSERVABLE): sets `WS-LOB-CODE = 'COM'`,
`WS-ROUTE-METHOD = 'DEFAULT'`, `ADD 1 TO WS-DEFAULT-COUNT`, DISPLAYs
`'WARN: DEFAULTED CLAIM '`. Source comment: *"SHOULD NEVER OCCUR — all claims
should have either a CMS contract ID or a mapped payer contract."*
- **INFERRED (PLAUSIBLE):** any claim reaching this path is a data-quality signal,
  not normal flow; silently defaulting undetermined claims to Commercial/MiCPS
  could mask government claims that fail identification. Confirm intended handling
  with SME.

`3500-CHECK-CLAIM-AGE` (OBSERVABLE): computes days between `ECL-DOS-FROM` and
`ECL-RECEIPT-DT`; if greater than `WS-STALE-CLAIM-DAYS`, `ADD 1 TO WS-STALE-COUNT`
and DISPLAY a warning. **Does not change routing.**

`4000-ROUTE-CLAIM` (OBSERVABLE): if `ECL-BILLED-AMT > WS-HIGH-DOLLAR-LIMIT`,
`ADD 1 TO WS-HIGH-DOLLAR-COUNT` and DISPLAY (does not change routing). Then
`EVALUATE TRUE`: `LOB-COMMERCIAL` → `4100`; `LOB-MEDICARE-ADV` → `4200`;
`LOB-MEDICAID` → `4300`; OTHER → `9100-ROUTING-ERROR`.
- **INFERRED (PLAUSIBLE):** the `WHEN OTHER` → `9100` path is effectively
  unreachable *unless* `PCT-LOB-CODE` from the payer-contract table contains a
  value outside {COM, MA, MC}, because `3300` otherwise forces `COM`. So `9100` is
  a defensive guard against **bad reference data** in `PAYER-CONTRACT`. Confirm.

`4100-WRITE-COMMERCIAL` (OBSERVABLE): comment "ROUTE TO MICPS COMMERCIAL INTAKE";
`WS-PLATFORM-CD = 'MICPS'`; WRITE `COMMERCIAL-CLAIM-REC FROM EDITED-CLAIM-REC`;
FILE STATUS check, ABEND on failure; `ADD 1 TO WS-COMMERCIAL-COUNT`.

`4200-WRITE-MA` (OBSERVABLE): comment "ROUTE TO FACETS MA INTAKE";
`WS-PLATFORM-CD = 'MIFCT'`; WRITE `MA-CLAIM-REC`; FILE STATUS check; count.

`4300-WRITE-MEDICAID` (OBSERVABLE): `WS-PLATFORM-CD = 'MIFCT'`; WRITE
`MEDICAID-CLAIM-REC`; FILE STATUS check; count.
- **Stale-comment finding (Rule 6):** the paragraph comment reads *"ROUTE TO
  STATELINK MCO PLATFORM"*, but the code sets platform `'MIFCT'`. The **code is
  authoritative** — Medicaid routes to MiFCT. The comment names a system
  (`STATELINK`) that does not appear anywhere else in the current knowledge
  estate and appears to be drift from an earlier platform. It may still reveal
  original intent/history; flag for SME.

`5000-WRITE-AUDIT` (OBSERVABLE): `EXEC SQL INSERT INTO MIVANCPS.ROUTING_AUDIT`
with the routing detail; checks SQLCODE.

`9000-FINALIZE` (OBSERVABLE): closes all files, DISPLAYs all counters, moves
`WS-ERRORS` to `RETURN-CODE`.

`9100-ROUTING-ERROR` (OBSERVABLE): DISPLAYs error with claim ID + LOB code;
`ADD 1 TO WS-ERRORS`.

`9999-ABEND` (OBSERVABLE): DISPLAYs `WS-ABEND-MSG`, `MOVE 16 TO RETURN-CODE`,
`STOP RUN`.

**Overall: HIGH.** MEDIRTR0 is small and structurally clean (clear paragraph
hierarchy, FILE STATUS and SQLCODE checks, an ABEND handler), so the *code* is not
the obstacle. The risk is entirely in what surrounds it: undeclared dataset
coupling, reference-data assumptions, missing layouts/values, and a routing
specification that the authoritative L3 document currently describes incorrectly.

**Recommendation: BLOCKED** until the following are resolved:
1. Ghost **FACETS-LOB-ROUTING-TABLE** — routing-table contents, maintenance
   procedure, actual queue/dataset names, and effective-date handling.
2. The three COPYBOOKs and the `WS-STALE-CLAIM-DAYS` / `WS-HIGH-DOLLAR-LIMIT`
   literal values.
3. SME ruling on the missing effective-date check in `3200` (defect vs handled
   upstream) — this changes correctness, not just documentation.

**Migration-wave cross-reference (finding):** MEDIRTR0 is **not** assigned to any
MiCPS L4 Wave 1–5 (those waves are MiCPS-internal). It sits on the MiEDI/MiFCT
perimeter, which is covered by ghost **MIFCT-MODERNIZATION** ("not yet scoped").
The HIGH/BLOCKED rating here argues this router must be scoped *before* the MiFCT
modernization program, since every LOB depends on it routing correctly.
